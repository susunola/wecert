# 期望状态来源（Desired-State Providers）

> **状态：设计草案，尚未实现。**
> 本文讨论"在某处新增一个域名，证书自动签发"，而不是"过期自动续签"。
> 语言跟随代码注释使用中文；若需要公开的英文版可以再出一份。

---

## 0. 结论先行

**这不是签发问题，是"期望状态从哪来"的问题。**

wecert 今天已经能做到"域名集合变了 → 立刻重签"（`CoverageDrift`，见
`internal/acme/manager.go`）。缺的完全在上游：让新域名进入期望状态。

关于"DNS 记录 ∩ CLB 规则"这个想法：**方向对，但它不是最优解。**
它属于下面三种架构里的 A 类 —— 让 wecert 自己去**推断**意图。
更好的做法是换一个轴：**让意图显式声明，并把"推断"从 wecert 里搬出去。**

| | 取向 | 一句话 |
|---|---|---|
| A | wecert 自己推断 | 观察两个副作用（DNS、CLB），反推意图，取交集 |
| B | 意图显式化 | 用 `_wecert` TXT 记录直接声明"我要证书" |
| **C** | **推断与生命周期分离** | **一个独立的 onboarding 组件推断意图并写出期望状态文档；wecert 只读文档做收敛** |

**推荐 C。** A 和 B 都可以作为 C 里面那个 onboarding 组件的实现。

## 1. 已有基础

不必从零开始。现状：

| 能力 | 位置 | 说明 |
|---|---|---|
| 域名集合漂移检测 | `acme.CoverageDrift` | 线上证书的 SAN ≠ 配置 → 立即重签 |
| 事件触发 | `POST /hook/reconcile` | 外部可以按需触发一轮收敛 |
| 单证书并发闸门 | `reconcile.Reconciler` | 定时器与事件触发不会重复下单 |
| 收敛循环 | `reconcile.RunAll/RunCert` | 已经能收敛任意的 `[]config.Certificate` |

**结论：`internal/reconcile` 几乎不用改。** 它已经能收敛任何一份期望状态，
问题只在于今天这份期望状态来自一个静态 YAML。

## 2. 三种架构取向

### 取向 A：wecert 自己推断（DNS ∩ CLB）

wecert 周期性枚举 DNS 记录和 CLB 规则，取交集，推断出"这些域名要证书"。

**这是被动观察两个副作用去反推意图。** 真值表：

| CLB 规则 | DNS 解析 | 含义 | 取交集 |
|---|---|---|---|
| ✓ | ✓ | 规则配了、名字也真的指过来 | **签发** |
| ✓ | ✗ | 规则配了，DNS 还没切过来 / 指错了 | 不签 |
| ✗ | ✓ | DNS 有记录但没在服务（悬空、他人记录、临时记录） | **不签** |
| ✗ | ✗ | 无关 | 不签 |

**收益是真实的**：第 3 行挡住了最危险的一类 —— 拼写错误、下线未清理的悬空记录、
别人留下的验证记录。而且爆炸半径小：一个有 bug 的脚本创建 500 条 DNS 记录，
没有对应规则 → 交集为空 → **0 次签发**，而不是 500 次。

**但它的固有弱点：**

1. **意图是推断出来的，不是声明的。** 我们永远在猜别人工作流的副作用。
2. **两个依赖。** DNS 枚举或 CLB 枚举任一故障，期望状态就算不出来。
3. **通配符有洞。** `*.example.com` 没有对应的 DNS 记录可查，
   DNS 这一侧的校验退化成"zone 存在"，等于没有检查。
4. **元数据无处依附。** 规则只告诉你 hostname，不告诉你 profile、
   keyType、和谁分在一组。

### 取向 B：意图显式化（`_wecert` TXT 声明）

把"我要证书"变成一条显式记录，而不是从副作用推断：

```
_wecert.example.com.        TXT  "wildcard=*.example.com,profile=classic"
_wecert.api.example.com.    TXT  "profile=tlsserver"
```

wecert 枚举 `_wecert.*` 记录 → 那就是期望状态。

**为什么这比 A 好：**

| | A：DNS ∩ CLB | B：`_wecert` TXT |
|---|---|---|
| 意图 | 推断 | **显式** |
| 依赖数 | 2 | **1** |
| 通配符 | 有洞，需另补标记 | **天然无洞** —— 标记本身就是声明 |
| 元数据 | 无处依附 | **TXT 内容就是载体** |
| 与 DNS-01 的关系 | 两条独立信息 | **同源**：声明和验证在同一个 zone |
| 误创建风险 | 中 | **低**（TXT 是明确的动作） |
| 额外动作 | 无 | 加一条 TXT |
| 枚举成本 | 2 次 API | 1 次 API |

**关键论点：DNS zone 本来就是这个系统的信任根。** 谁能写这个 zone，
谁本来就能为其中任何名字做 DNS-01 验证、从任何 CA 拿到证书。
把声明也放在这里，**没有引入新的信任边界**，只是把已经存在的能力显式化。

**代价是"多一步"。** 但为证书增加一道显式动作，我认为是特性不是负担 ——
证书是安全相关资源，"没有明确说要"就不该发。

**需要注意的：** 标记本身也可能被误删 → 触发删除路径。
所以删除保守性（见 §5）对 B 同样适用。

### 取向 C：推断与生命周期分离 ★ 推荐

**核心原则：wecert 永远不推断。某个东西负责推断，并把结论写下来。**

```
┌──────────────────────────────────────────────┐
│  onboarding 组件（可替换、可试错、可丢弃）      │
│    - 枚举 DNS / CLB / CMDB / git ...          │
│    - 套用分组策略、通配符优先                   │
│    - 骤变熔断、配额预算                         │
│    - 写出期望状态文档（可 diff、可 review）      │
└────────────────────┬─────────────────────────┘
                     │ 期望状态文档（契约）
                     ▼
┌──────────────────────────────────────────────┐
│  wecert（保持不变）                            │
│    - 只读期望状态，做收敛                       │
│    - 签发 / 续期 / 部署 / ARI                  │
└──────────────────────────────────────────────┘
```

**为什么这是架构上更优的分解：**

1. **wecert 的输入永远是显式的。** 它不做任何启发式判断 ——
   而现在这个系统所有已知的坑（限速、误删、状态漂移）都出在"判断"上。
2. **推断逻辑和证书生命周期解耦。** 推断逻辑必然会反复改（加来源、调阈值、
   修边界），而证书生命周期必须稳。混在一起，改推断就是在动签发。
3. **期望状态是个文件 → 可 review、可 diff、可回滚、可审计。**
   "上周二为什么多签了一张证书" 可以直接 `git log` 那份文档。
4. **熔断发生在正确的位置。** 期望状态的骤变应该在**写文档**那一步被拦住，
   而不是等 wecert 读到一份已经塌掉的期望状态再补救 —— 那时候已经晚了。
5. **wecert 不引入第二个来源依赖。** 来源故障只影响 onboarding 组件，
   而它的失败模式是"期望状态不更新"，**是安全的**（保持现状）。
   相反，如果 wecert 自己枚举来源，来源故障可能被误读成"域名消失了"。

**A 和 B 在这个架构里的位置：** 它们都是 onboarding 组件的**可选实现**。
所以 C 不否定前两个 —— 它只是把它们放在了正确的地方。
可以先用 A 或 B 跑起来，将来换别的来源，wecert 一行不改。

**C 的代价（诚实地说）：**
- 多一个组件要维护
- 期望状态成了派生产物，git 里会有机器写的提交
- 需要定义契约（文件格式 / API）

**什么时候 A 反而更合适：** 如果你不想多一个组件，且来源很稳定，
把推断放进 wecert 是可接受的。但要接受它的四个固有弱点。

## 3. 守卫：CLB 与 DNS 在 C 里的位置

换到 C 之后，CLB 规则和 DNS 记录**不再是意图来源，而是守卫**：

| 角色 | 由谁承担 |
|---|---|
| **意图 + 元数据** | `_wecert` TXT 声明（或 onboarding 组件自己的登记） |
| **守卫 1（可选）** | CLB 规则存在 —— "确实在服务" |
| **守卫 2（可选）** | A 记录能解析 —— "确实指向我" |

守卫是**前置条件**，不是来源。这个区别很重要：
- 作为来源，它们要参与"推断意图"，承担推断的全部风险
- 作为守卫，它们只负责**否掉**已经声明的意图，失败模式安全得多

建议默认：**声明必需 + 守卫 1 必需 + 守卫 2 可选**。

## 4. 契约

```go
// Package spec —— 期望状态来源的抽象。
//
// 实现必须满足两条性质：
//   1. 幂等：同样的输入永远给出同样的输出（顺序也一致）
//   2. Name 稳定：证书身份不能因为域名集合变化而改变
type Provider interface {
    Desired(ctx context.Context) ([]config.Certificate, error)
}

// Decision 记录每个 hostname 的去留理由。
//
// 必须一并返回 —— 否则"我加了域名怎么没签"会成为反复被问的问题，
// 而且排障只能靠翻日志。
type Decision struct {
    Hostname string
    Included bool
    Reason   string          // "no _wecert marker" / "no CLB rule" /
                             // "debouncing" / "quota fuse" / "source unknown"
    Details  map[string]any
}

type Result struct {
    Certificates []config.Certificate
    Decisions    []Decision
}

type ReportingProvider interface {
    Provider
    // DesiredWithReasons 是推荐的入口；Desired 只是它的简化形式。
    DesiredWithReasons(ctx context.Context) (*Result, error)
}
```

### ⚠️ Name 稳定性（最容易被忽略、后果最严重）

```go
// 错的：名字随域名集合变化
Name: strings.Join(sortedDomains, "+")     // 加一个域名 → 名字变了

// 对的：名字从分组键推导
Name: "example-com"                        // 域名怎么加删，名字不变
```

**为什么这是致命的：** 如果 name 随域名集合变化，那么加一个域名会让状态库里
凭空多出一条新记录，而旧那条的 order URL、ARI certID、deployed CertID
**全部成为孤儿**。"每张证书最多一个进行中的订单"这条不变量因此失效 ——
两边的订单会同时飞，直接撞上 exact-set 限速。

## 5. 五条必须钉住的安全不变量

这五条是这套设计里所有已知危险路径的清单。**任何一条不做好，
自动签发都不该上线。**

### 5.1 来源查询失败 ≠ 名字消失了

**这是唯一能造成灾难的地方，必须写在最前面。**

```
DNS 枚举接口抖动 → 返回空 → 若被理解成"这些名字都没了"
                 → 期望状态里没有域名了
                 → CoverageDrift 认为集合变了
                 → 重签一张不含域名的证书 / 把域名从证书里摘掉
                 → 线上立刻握手失败
```

**这比不签发严重得多。**

三态语义：

| 来源返回 | 语义 | 动作 |
|---|---|---|
| 有数据，且某名字不在其中 | **确认不存在** | 可驱动删除（仍需宽限期） |
| 查询报错 / 超时 / 部分失败 | **未知** | **保持现状**，不动期望状态 |
| 全量成功但结果为空 | 需区分真空 vs 异常 | 见 5.2 |

### 5.2 期望状态骤变熔断

集合规模在短时间内掉超过阈值（建议 30%）→ **停下来告警，不要照做**。

正常的一次下线不会让集合少三成。突然少三成，几乎一定是上游出了问题
（API 返回不完整、权限被改、zone 读失败）。这种情况下"照做"的后果是
批量摘除 SAN → 批量站点握手失败。

**冻结比执行安全。**

### 5.3 删除比增加保守一个量级

**增加是收敛，删除是决策。** 两者保守程度应该差一个数量级。

双来源或"声明 + 守卫"的结构会让状态抖动：

```
t0: 加声明            → 不签（守卫未就绪）     正确
t1: 加 CLB 规则        → 签发                  正确
t2: DNS 传播抖动一下    → 若立刻删域名 → 重签   ✗ 白烧配额
t3: DNS 恢复           → 又重签                 ✗ 再烧一次
```

**一次上线触发三次签发。** 所以删除必须：

- **所有来源都确认缺失**（不是"查不到"，是真的查过且没有）
- 且**持续缺失超过宽限期**（建议 24h 起，按变更频率调）
- 缺失状态**落盘**，不能靠内存
- 移除前做**引用检查**：还在被监听器/规则引用就不动

### 5.4 配额熔断

域名集合变化**不算同名续期**，实打实消耗
`Certificates per Registered Domain`（50 / 7 天，跨账号共享）。

必须有：
- **去抖**：5~10 分钟窗口内的多次变更合并成一次签发
- **排队与限速**：新增排队，不并发打出去
- **预算**：单位时间最多允许多少次集合变化，超了就冻结告警
- **通配符优先**（见 §6），这是省配额的根本手段

### 5.5 显式授权

不是"DNS 里有就签"，而是"**标记了才签**"。
来源只提供线索，授权必须是一个明确的动作。

护栏：
- 允许清单：只对指定 registered domain 生效
- 上限：单位时间新增上限，超限冻结
- 审计：谁在什么时候加了什么，全部落盘

## 6. 分组与速率限制的算术

这是决定方案可行性的硬约束，不是优化项。

### 6.1 通配符优先 —— 让"加域名"大多数时候不需要签发

| 场景 | 无通配符 | 通配符优先 |
|---|---|---|
| 加 `foo.example.com`（已有 `*.example.com`） | 1 次重签 | **0 次** |
| 加 `a.b.example.com`（只有 `*.example.com`） | 1 次重签 | 1 次（需要 `*.b.example.com`） |
| 批量导入 50 个子域 | **50 次重签 = 撞满配额** | **0 次** |

**这是整个设计里最值钱的一条。** 它把"动态加域名"从"每次都要签发"
降级成"大多数时候什么都不用做"。

### 6.2 分组策略

1. 按 **registered domain** 分组（用 Public Suffix List，LE 也是这么算配额的）
2. 组内**优先用通配符表达**，只有出现新的二级命名空间才真正签发
3. 单证书域名数上限按 profile：`classic` 100 / `tlsserver` 25
4. **建议上限取 25**，与 `tlsserver` 对齐 —— 将来切 profile 不用改架构
5. 记住爆炸半径：**同证书的域名生死与共**

### 6.3 配额预算怎么估

假设每张证书每天一次集合变化的极端情况 × N 张证书 —— 必然撞限。
所以要反过来算：**你这周能承受多少次集合变化？** 50 是上限，留一半余量，
实际预算 25 次/周。超过就该去申请 LE 的 rate limit override，
或者接受"变更排队到下一周"。

## 7. 可观测性契约

这类系统上线后，**"我的域名为什么没签出来"是头号问题**。
没有专门的可观测性设计，会被反复问，而且只能靠翻日志。

必须能回答：

| 问题 | 数据来源 |
|---|---|
| 期望状态是什么？ | `DesiredWithReasons` 的 `Certificates` |
| 实际证书覆盖什么？ | 状态库 `cert_pem` 的 SAN（已有） |
| 差异在哪？ | `CoverageDrift` 的 detail（已有） |
| 某个域名为什么没进去？ | `Decision.Reason` |
| 为什么现在没签？ | 退避窗口 / 去抖窗口 / 配额熔断 / 等守卫 |
| 上次变更是什么时候、因为什么？ | 决策日志（需新增） |

建议加一个只读诊断端点（或扩展 `GET /hook/status`），直接返回三者对比。
排查成本会低一个数量级。

## 8. 分阶段落地

| 阶段 | 内容 | 为什么是这个顺序 |
|---|---|---|
| **0** | **GitOps + 现有 webhook** | 零开发量。域名写 git，merge 后 CI 调 webhook。先验证流程和人的习惯 |
| **1** | **Provider 抽象** + 一个只读来源，**只检测与告警，不自动签** | 观察真实世界的漂移频率和形态。数据会告诉你配额够不够、去抖窗口该多大、有没有批量导入 |
| **2** | 通配符优先的分组策略 | 把"加域名"的成本降到接近零 |
| **3** | 打开自动签发 + 去抖 / 排队 / 熔断 | 到这一步你已经有数据支撑参数了 |
| **4** | 删除宽限期与引用检查 | 删除比增加危险，放最后并做保守 |

**阶段 1 的"只告警不自动签"是最想强调的一步。**

直接上自动签发，你会在完全不了解真实漂移形态的情况下把配额赌进去。
先跑两周只读，你会知道：一天漂移几次、有没有批量导入、有没有奇怪的记录。
这些数据直接决定去抖窗口、分组大小和熔断阈值 —— **没有它们，
参数只能靠猜，而猜错的代价是账号级的限速。**

## 8.1 实现状态

阶段 1~4 都已落地，来源采用"**取向 B 作为取向 C 里的来源**"：

| 阶段 | 状态 | 落在哪里 |
|---|---|---|
| 0 GitOps + webhook | 已有 | 配置里的 `certificates` + `POST /hook/reconcile` |
| 1 Provider 抽象 + 只读来源 + 只告警 | **已实现** | `internal/spec`（契约/文档/Provider/Observer）、`cmd/wecert-onboard`、`desiredState.mode: observe` |
| 2 通配符优先分组 | **已实现** | `internal/group`（PSL 注册域 + 单层覆盖计算） |
| 3 自动签发 + 去抖/排队/熔断 | **已实现，但默认关闭** | `internal/onboarding` 的骤变熔断与配额预算；`mode` 默认 `static`，要显式切 `enforce` |
| 4 删除宽限期与引用检查 | **已实现** | `internal/onboarding`：确认缺失 + 宽限期 + CLB 引用检查，三者同时满足才移除 |

五条安全不变量在代码里的落点写在 `internal/onboarding/onboard.go` 的包注释里。
日常操作、切换步骤与排障见 [`desired-state.md`](desired-state.md)。

**和设计的一处偏离：** 第 5.4 条提到的"去抖窗口"没有单独实现，
而是由 onboarding 的**定时器周期**承担 —— 它是一个一次性进程，
跑完就退出，两次运行之间的窗口天然就是去抖窗口。
把它做进进程里只会引入一份额外的状态和一类新的时钟 bug。

**仍然没做：** 外部黑盒探测（拨 443 读 `notAfter`）、
`multi_cert_info` 的"一张证书不影响另一张"验证、
DNSPod token 走 `LoadCredential`。

---

## 9. 明确不做的

- **不做"DNS 有记录就自动签"。** zone 里 MX/TXT/SPF/验证记录全在里面，
  DNS 记录 ≠ 想要证书。必须有显式授权。
- **不做"新增域名立刻签"。** 必须去抖。一次批量变更可能产生几十个域名，
  逐个签会直接撞配额。
- **不做"来源删了立刻从证书移除"。** 必须宽限期 + 引用检查。
- **不让 wecert 自己推断意图**（除非明确接受取向 A 的四个弱点）。
- **不在来源不可用时降级成单来源。** 降级会让安全性随故障一起消失，
  而你恰好在那时最需要它。**一律冻结。**
