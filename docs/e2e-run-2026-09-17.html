怎么测的what is real, and what is not

这一轮里每一个"真实"都写明了边界。评审时最该看的是下面这张表：哪些部件真的在跑，哪些是替身，以及替身各自对应到哪条验收路径。

部件这一轮实际用的是什么
acme_serverpebble, validation DEGRADED (the CA did not read the record)
deploydisabled (deploy.Noop): no Tencent Cloud credentials in a test environment
dnsauthoritative test server on 127.0.0.1:53
dns_providerlego httpreq -> the test authority's /present, /cleanup
transportsauthority answered over udp; tcp: tcp: dial tcp 127.0.0.1:53: i/o timeout
关于 CA 校验（这一轮最需要看清的边界）。pebble's validator forces TCP whenever a custom resolver is configured (va.go: if customResolverAddr is non-empty, va.dnsClient.Net = "tcp"), and this host cannot carry TCP on port 53: the bind succeeds and the traffic never arrives (tcp: dial tcp 127.0.0.1:53: i/o timeout). So the CA accepted the challenges without reading them, and PEBBLE_VA_ALWAYS_VALID was set for this run. Everything on wecert's side is still real -- the solver wrote the records through a real lego provider, and the production propagation check read them back over UDP, which the per-case evidence below shows -- but "the CA validated the record" is NOT one of the things this run proves. On a host where TCP/53 works (Linux with CAP_NET_BIND_SERVICE, for example docker run --cap-add=NET_BIND_SERVICE) the same suite runs with real validation and the report says so.

未跑的部分not run, and why

这几项属于"需要真实云凭证或真实域名"，本环境没有，所以它们没有被算进上面的通过数。每条都给出可直接执行的命令。

cloud-deploy-and-rebind需要凭证

Upload to Tencent Cloud SSL and rebind the CLB listener, then read the binding back from the API.

  • needs TENCENTCLOUD_SECRET_ID/KEY with the CAM policy in deploy/, plus a CLB and an HTTPS listener: scripts/run-stage-ab.sh
lets-encrypt-staging-issuance需要凭证

The same lifecycle against Let's Encrypt staging with a real DNSPod or Tencent Cloud DNS zone.

  • needs a real zone plus DNS API credentials and outbound DNS: cp e2e-config.example.yaml e2e-config.yaml && ./scripts/e2e-test.sh <domain> ./e2e-config.yaml
black-box-probe-of-the-live-endpoint需要凭证

Dial 443 and compare the certificate served with the one deployed.

  • needs a deployed certificate behind a CLB: ./bin/wecert-probe -host <name> -min-valid 168h
binary-against-a-local-ca本机无法运行

Run the compiled wecert binary, rather than the Manager in-process, against pebble.

  • the binary builds its own ACME HTTP client with no CA override, and on macOS Go ignores SSL_CERT_FILE (verified: GODEBUG=x509usefallbackroots=1 has no effect without SetFallbackRoots, which this program does not call). On Linux, SSL_CERT_FILE is honoured, so the same run works in CI.
生成方式：make e2e（scripts/e2e.sh → scripts/e2e-report.py）。 原始数据：dist/e2e-go.json（用例与 DNS 查询日志）、dist/e2e-extras.json（套件与宿主）。 报告只呈现这次运行真实产生的结论。
