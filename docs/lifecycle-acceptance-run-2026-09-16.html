TL;DR三句话结论

  • 系统整体行为正确：首签、幂等、SAN 增删、wildcard 与 apex 共享一个 TXT 名、 并发双证书、ARI 与时间两条续期路径、中断续跑、孤儿行回收、声明层 observe→enforce→下线→冻结， 共 16 个阶段通过，且每个阶段的状态断言（订单数、授权行、DNS 残留、指标）都成立。
  • 但换域名这条路是死的：漂移分支无条件把旧证书的 ARI certID 当 replaces 发出去， 零重叠时 Let's Encrypt 直接 400 拒绝 newOrder；而 ari_cert_id 只在签发成功后重算， 于是每一轮都失败——证书永久无法更换域名，且 -once 仍返回 0。已修并合并（PR #45）。
  • 用例本身也要修：6 处错误，其中 3 处是"当初设计的测试手法根本无效"——最典型的是 "让递归解析器指向黑洞地址来制造中断"，实测会让 provider 连 TXT 都写不下去。已修（PR #46）。

Method怎么测的

用例的全部阶段都在 Let's Encrypt staging 上跑（先用锚定 directory: 的正则过闸）， 挑战记录写进真实 DNSPod 区域，全程 deploy.enabled: false，因此不上传任何云证书、 不消耗生产配额。被删改的只有三样东西：配置里的域名列表、DNSPod 上本用例自己建的 TXT 记录、 以及测试状态库（/tmp 下的一次性 SQLite）。没有动测试环境里的 CLB 与 CVM。

grep -qE '^[[:space:]]*directory:.*acme-staging' "$A_CFG" || { echo "拒绝运行"; exit 1; }

怎么"制造一次崩溃"

崩溃恢复是这次的重点，而"掐时间 kill"听起来不可靠，所以第一版设计了一个看似更干净的手法： 把 dns.recursiveNameservers 指向 192.0.2.1（TEST-NET-1，永远不可达）， 指望进程"写完 TXT、落完库，卡在传播确认"。

实测证明这个手法是错的：

present TXT (wild.atomwangnus.com): present TXT: tencentcloud:
  failed to get hosted zone: could not find zone

原因在 internal/acme/dns.go：那个解析器列表会被灌进 lego 的全局解析器 （dns01.AddRecursiveNameservers），而 lego 的 provider 在写记录之前 要用它查一次 zone。黑洞地址把 provider 一起打断了，TXT 根本没写下去——想要的中间态永远不存在。

最终改用 kill -9，并在动手前量了窗口：从 TXT presented 到这一轮结束有 23.5 秒，完全够一个 grep 循环看到日志再发信号。杀完还强制校验前置态 （授权行 presented=1 且 TXT 真在 DNS 里），不成立就重来。

Interrupt windowA4 中断窗口实测

用例要的是"TXT 已经在 DNS 里、进程还没走完"这个中间态。它有多宽，决定了这个测试是否可靠—— 所以先从实测日志逐行取时间戳，而不是估算。

Finding 1 · Code defect发现① 证书永久无法更换域名

A4b 把一个已经签发的证书换到一组完全不相交的域名上，订单创建被 Let's Encrypt 直接拒绝。 这不是一次失败，而是一个不会自愈的循环。

现场证据（修复前）

level=ERROR msg="pass failed; a retry has been scheduled" cert=lifecycle
  err="create order: acme: error: 400 :: POST :: https://acme-staging-v02.api.letsencrypt.org/acme/new-order
    :: urn:ietf:params:acme:error:malformed
    :: Could not validate ARI 'replaces' field
    :: identifiers in this order do not match any identifiers in the certificate being replaced"
  consecutiveFailures=1 nextAttemptAt=2026-09-16T17:18:04+08:00

$ sqlite3 a.db "SELECT name, consecutive_failures, ari_cert_id FROM certificates; SELECT count(*) FROM orders;"
lifecycle|1|3tpCJfI0wCebZhbPZWqQrCHVMIc.LCmKUKocV8oEVhEAaYwRfYIL
0

orders=0 是这条缺陷的关键指纹：订单根本没被创建， 所以 ari_cert_id 没有任何机会被刷新，consecutive_failures 只会一路累加。 另外注意 -once 此时仍返回 0——单张证书的失败被刻意丢弃， 所以任何靠退出码判断健康度的巡检都看不见这件事。

修复

两处，改在 internal/acme/manager.go 与 manager_renew.go：

// manager.go —— 漂移分支不再发送 replaces
} else if drifted, detail := CoverageDrift(leaf, c.Domains); drifted {
    m.log.Warn("the live certificate's SANs no longer match the config; reissuing now", …)
-   return m.issue(ctx, c, st, st.ARICertID)
+   return m.issue(ctx, c, st, "")
// manager_renew.go —— 兜底：被拒就丢掉 replaces 重试一次（覆盖续期路径）
order, err := m.core.NewOrder(c.Domains, &api.OrderOptions{Profile: c.Profile, ReplacesCertID: replaces})
+ if err != nil && replaces != "" && mentionsReplaces(err) {
+     m.log.Warn("the CA refused the ARI replaces field; retrying the order without it …")
+     order, err = m.core.NewOrder(c.Domains, &api.OrderOptions{Profile: c.Profile})
+ }

兜底是刻意的：丢一次豁免只花一个配额，续不上是另一回事。 判断用 strings.Contains(err, "replaces")——误判的代价是"多一次 newOrder"，漏判则退回今天的行为， 两种都不会写坏状态，所以不值得为它引入一个 lego 类型化错误。

③ 测试手法无效 · A4 / A9

黑洞递归解析器做不出想要的中断

症状
failed to get hosted zone: could not find zone，TXT 从未写入
原因
dns.recursiveNameservers 被灌进 lego 全局解析器（dns01.AddRecursiveNameservers），provider 写记录前要用它查 zone
修正
改用 kill -9，并给出实测窗口 11.2s / 23.5s 与前置态校验
④ 前提假设错 · A4

"apex + 通配"不一定产生两个挑战

症状
预期 2 条 TXT，实际只有 1 条（TXT propagated records=1）
原因
Let's Encrypt 复用仍然有效的授权（同账号 + 同 identifier，约 30 天）；apex 在 A0 已验证过
修正
改用一对从未验证过的标识（wild.$APEX 与 *.wild.$APEX），并写明 records=N 是挑战数不是 SAN 数
⑤ 未说明的竞态 · A5

LE 报 NXDOMAIN，而权威探测明明看到记录

症状
DNS problem: NXDOMAIN looking up TXT for _acme-challenge.wild…，同一时刻权威 NS 返回 2 条 TXT
原因
DNSPod 的 NS 最终一致；就绪检查按设计容忍从本机不可达的 NS（实测 10 个地址有 4 个不可达），而 LE 能到达它们
修正
用例写明"这是重试场景，不是缺陷"：该轮记一次失败 → 重试时订单已被判 invalid 并丢弃 → 新订单成功
⑥ 脚本写法错 · A6

等待条件把第二张证书打断了

症状
第一张签发成功后脚本立即跳出等待，杀进程时第二张还在验证中
原因
把两张证书的 not_after 拼成一个字符串再比 !=，任一张变化就成立
修正
改为逐张计数（not_after > 上一轮最大值 的行数必须等于 2）
⑦ 忽略了熔断 · B4

3 条声明删 1 条 = 33%，直接被冻结

症状
mode=frozen: the declared name set dropped from 3 to 2 (33%, threshold 30%)，文档不动
原因
熔断阈值是"单轮跌幅 > 30%"，声明条数少时一次正常下线就会触发
修正
用例写明：声明 4 条以上（25%，最忠实），或显式传 -drop-threshold；并单独把这次 33% 冻结记录为"熔断按设计工作"
⑧ 观测信号错 · B5a

wecert_desired_state_frozen 永远是 0

症状
onboard 已冻结（退出码 2、文档未更新），但 wecert 侧该项指标仍是 0
原因
wecert 只看到"文档仍然有效"，它无从知道写入方那一轮冻结了
修正
真正的运维信号是 wecert_desired_state_age_seconds 持续增长；用例判据已改，并删掉了失效的日志 grep

Environment环境观察

权威 NS 可达性：10 个地址里 4 个不可达

6 可达
4 超时

这是就绪检查"容忍不可达 NS"的直接后果，也是 A5 那次竞态的根因：我们看不见的 NS 可能还没同步， 而 LE 看得见。用例因此不能把"权威探测通过"当成"LE 一定能验证通过"。

另外两点

  • 负缓存 180 秒：DNSPod 的 SOA minimum 是 180s，递归解析器会据此缓存 NXDOMAIN。 记录删除后一段时间内，递归侧仍会返回否定答案——判断"记录在不在"必须问权威 NS。
  • LE 复用授权：同一账号 + 同一 identifier 的有效授权在约 30 天内被复用， 所以"域名数量"与"写了几条 TXT"没有对应关系（A2 里 2 个 SAN 只写了 1 条， A7 的续期甚至是 status=ready 直接下发、零挑战）。
